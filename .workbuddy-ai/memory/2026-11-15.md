### 系统修法（提交见 git log）
1. **统一收口**：解析 4 个树访问器（`GetAbsoluteRect/GetID/GetChild/GetCount`）
   后，把 `p_abs_rect/p_ctrl_id/p_ctrl_child/p_ctrl_count` 指向校验包装。
   `ctrl_object_ok()` 校验对象 `probe_mem_ok(0xb0)` 并沿 +0xa0 走 8 层
   parent 链（镜像引擎递归）。一次覆盖全文件 50+ 处调用点，不合格返回
   空 rect / 0 / NULL，绝不进引擎。
2. **第二条路径**：`abs_rect_call()` 那条走 x8 间接结果的汇编 trampoline
   也在入口加了同一个校验（3 处使用）。
3. **事件分发**：5 处 `colevent_real(...)` 改走 `safe_colevent`；
   `nx_ControlObject_EventProc` 入口拒绝无效 obj；
   `nx_TouchHandle_Event` 入口/最终调用前拒绝无效 root（含 box/live/
   topmost layer 替换后的值）；`popup_base_real()` 的 box 也升级校验。
4. **场景切换清缓存**：新增 `scene_caches_reset()`，在 FLOW_WRAP 的
   MAP_Load 分支和检测到 stale root 时调用，清 quick_objs / last_good_root /
   nav_* / pending_ctl / bin_del_ctl / hud_* / shop_btn_seen 等。
5. 其它单点：`desc_scroll_tick` 的 sc、`kill_stale_overlay` 的
   `p_delete_child(root,c)` 都补了校验。

## 09:03 第五次实机崩溃（杂货商店出售，按「是」）

- 报告 `01708651048_*.log`，证据 `logs/crash-20261115-0903/`。
  日志尾部：`input: A/B now talk to the message box` → 商店图标资源加载
  `UI_shopicon_001/002.png` → 一串 FULLSCREEN quad → 崩。
  本轮日志里**没有** `save: bin tapped`，说明 08:46 的 bin 误判已修住。
- PC = **engine+0x13357c = `LINKEDLISTITEM_getData`** 的
  `ldr x0,[x0,#8]`；X0 = 1 → Address = 0x9（1+8）。
  X2 = engine+0x131668 = `ControlObject_GetChild` 地址，
  X17 = 0x13357c（PLT stub `br x17`，不改 LR），
  **LR = NRO `row_under+0xbc`**（反汇编 0x2998c = `blr x8` 的返回点，
  x8 是 `p_ctrl_child`）。栈：nx_TouchHandle_Event+0x658
  ← engine handleCletEvent+0x134 ← input_touch+0x230
  ← input_update+0x20a0 ← engine_main ← main。
- 引擎链表布局（已反汇编确认，别再猜）：
  - `ControlObject_GetChild`(0x131668)：读 `[obj+0x78]` 得 count，
    `obj+0xa8` 当内联 LINKEDLIST 传给 `LINKEDLIST_getHead`(0x132d48
    = `ldr x0,[x0]`)；节点 `+0x10` = next（getNext 0x133584），
    `+0x08` = data（getData 0x13357c）；list `+0x10` = size。
  - 崩溃即 list head 指针被复用成 1，引擎无检查就 getData。
- **共性**：又是「确认弹窗按是」(code 0x18 release) 触发的旧场景控件树
  遍历。`row_under()` 是**纯日志诊断**（返回值只用于打 log，第二处甚至
  `(void)` 丢弃），却在**任何页面**每次 release 递归整棵树。08:46 只给
  `note_bin_tap` 加了 `screen_has_save_rows()` 门控，漏了 `row_under`，
  于是商店页按「是」踩到同一个坑的另一条路径。

### 系统修法（这次覆盖点击路径全部树遍历）
1. `ctrl_object_ok()` 再加两层校验，使所有经包装的
   `p_ctrl_child()/p_ctrl_count()` 调用都受保护：
   - parent 链每层 `[+0x78]` 的 child count > 128 就拒绝；
   - 对象 `+0xa8` 的 list head 起，沿 `+0x10` next 走 8 个节点，
     每个都要 `probe_mem_ok(node,0x20)`。
   （正常控件 head 为 NULL 或堆节点；X0=1 会被挡住。）
2. `row_under()` 的两处调用都加 `screen_has_save_rows()` 门控 ——
   存档页专用诊断不该在商店/能力加点弹窗里跑。
3. 现有门控复核：`note_bin_tap` 已有页面校验 ✓；
   `is_save_page_hit` 只在 `select_scene_up` 时跑（class screen 下确有
   存档页），`find_save_row` 仅供 `screen_has_save_rows` 使用。

### 教训（写给自己）
「确认弹窗按是」= code 0x18 release，会触发 `nx_TouchHandle_Event`
尾部那一串诊断遍历。凡是**只为存档页服务**的树遍历，必须统一走
`screen_has_save_rows()`，否则每次加新页面都可能再崩一次。

## 12:18 商店出售（第 4 轮）：按「遮挡屏蔽」语义改为前置分发

用户建议「有弹窗时直接屏蔽被它遮挡的区域交互」。这个方向是对的。

### 为什么前一版仍会点到格子
新版 `e2764178` 日志（`logs/shop-sell-1120/debug-crosslayer.log`）：
- `ui: cross-layer button ... -> 1` 出现 6 次，`是否出售？` 确认框正常弹出
  → 说明 **r==0 时**兜底是有效的；
- 但「有时」点到格子 = 引擎的**格子命中盒比日志 rect 大**，点击被格子
  认领、`r != 0`，兜底根本不会执行。
- 静态回归证实：实际点击 (374,518)/(371,520)/(374,526)/(374,528)
  下**没有任何 74x74 格子的 rect 包含该点**，却仍被格子接走。
  → 所以「按点判断是否与格子重叠」的判据不可用。

### 修法（用户要的遮挡屏蔽）
1. 新增 `shop_page_has_grid(page)`：只要页面容器里有 ≥8 个
   74x74 `ControlItem`(0x13e36c) 格子，就判定为商店/背包页，
   **按页面整体**启用屏蔽，不依赖点命中。
2. `shop_button_pre_dispatch()` 前移到 `colevent_depth++` 之后、
   引擎默认分发**之前**：商店页里只要点击位置下有真正的
   `ControlButton`(0x13ddf4)（出售 / 是 / 否），就把事件直接交给它并
   return，背景格子层完全不参与分发。
   非商店页保持引擎原逻辑。
3. `r==0` 的跨层兜底保留作补充。

### 静态回归（最新快照 88 控件 / 32 个货物格）
`shop_page_has_grid = True`；所有实际点击坐标都解析到按钮：
| 点击 | 前置交给 |
