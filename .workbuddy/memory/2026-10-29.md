### 关键决策与发现（后续复用）

- **`.jpg` 是反解包伪装**：APK `assets/common/game_res/` 下 732 个文件全部以 `.jpg` 结尾，但 `UI_003.png.jpg` 实际是 PNG、`BGM05.jpg` 实际是 OggS。`libgame.so` 里**没有任何 `jpg` 字面量**，引擎代码请求的是 `m%d.dat` / `font.fnt` / `game.dat` 这类真名 → 打包时必须剥掉 `.jpg`。已写入 `tools/pack_data.py`。
- **资源路径三条回退链**（反汇编 `sub_24a400` 确认）：
  `resources/<lang>_r<res>/<cat>/<file>` → `resources/<lang>/<cat>/<file>` → `resources/common/<cat>/<file>`，`<cat>` = `game_res`。故 SD 布局为 `data/resources/common/game_res/`。
- **`texture.store`/`appinfo.dat`/`envinfo.dat`/`i_pack.dat`/`thpcheckslot*.dat` 不在 APK 里**，引擎用 `open(..., 0x242)`（O_RDWR|O_CREAT|O_TRUNC）自己创建缓存。
- **`nacptool` 的 `--titleid=` 有坑**：`sscanf("%016" SCNx64)` 的字段宽度把 `0x` 前缀也算进去，传 `0x010000000000F0A4` 会掉最后一位。必须去掉 `0x`。（`build.py` 已处理）
- **switch-tools 的 NRO 头部**：偏移 0 不是 `NRO0` 而是 crt0 写的 `b #0x80` + `modOffset` + `"HOMEBREW"`（16 字节 NroStart），`NRO0` 在 0x10，text 从 0x80 开始，ASET 在 `nro_size` 处。校验 NRO 时必须按这个布局读。
- **字体不用外挂 TTF**：`plInitialize` + `plGetSharedFontByType(PlSharedFontType_Standard)` + `FT_New_Memory_Face` 直接用主机共享字体，CJK 开箱可用。

## 真机突破：JNI_OnLoad 是缺失的关键入口

- **根因**：手动加载 .so 时从未调用 `JNI_OnLoad`。它的第一条指令就是 `str x0,[x8,#0x6a8]` 缓存 JavaVM；
  引擎 `jGetEnv` 后面从这个全局取 vm，因为没调用所以是 NULL → `ldr x8,[x0]` 解引用空指针 →
  真机数据异常（2168-0002）、Eden 卡死。补调之后 `CWrapperData.nativeInitialize` 直接通过，引擎跑起来。
- 已修：`input_bind` 在 finalize 之后读已失效的暂存符号表（真机必崩）；`so_finalize` 前把符号表搬到堆上；
  JNI 表 27–152 段按 `JNINativeInterface` 重建（原来整体错位一位，GetObjectClass 拿到 2）；
  `GetDirectBufferAddress/Capacity/NewDirectByteBuffer`（229–231）实现，事件初始化那两个 ByteBuffer 参数
  给真实 256KB/64KB 零缓冲区；`dispatch_object` 兜底不再返回 NULL；libHercules 默认不加载。
- 状态：Eden 完整启动（nativeStart 128ms / StartClet 8.5s / 60 frames done）；真机走到 `nativeStart`。
- **Eden 坑**：跑一次后 `sdmc/switch/inotia4/data` 会被清空（不是我们删的，无 unlink/rmdir 调用），
  所以每次测试前必须重新 `deploy.py --eden` 同步。

## 黑屏根因连环修复（本轮最大突破）

按重要性排序，全部已在 Eden 验证：

1. **`BIND_NOW` 未填 PLT 槽（最致命）**：libgame.so `DT_FLAGS=0x8`，模块内部导出的函数调用也走 PLT → GOT 槽。
   加载器只处理 `SHN_UNDEF` 符号，导致 **4871 个槽保持 0**，`br x17` 直接跳到地址 0。
   修：`so_resolve` 对 `st_shndx != UNDEF` 的 `JUMP_SLOT/GLOB_DAT` 写 `virtbase + st_value + addend`。
2. **`ActiveUser.jniInitialize` 从未调用**：`Java_com_com2us_module_activeuser_ActiveUser_jniInitialize(env,thiz,obj)`
   内部 `GetJavaVM` + `NewGlobalRef` + `GetObjectClass`，把 JavaVM 存到 `0x6e4940`。
   该全局是 `CS_ActiveUser*` 等一堆 CS_ 包装的第一步；为空 → `startClet` 第一次调用就跳到 0。
   这是"帧循环在跑但永不绘制"的直接原因。
3. **DRM `Protection` 层**：`nativeStartClet` 的真实逻辑是
   `startCheckSpeedHack(); if (isRunningMemoryHack()==1) { showDialogAndExit(0); nativeFinish(5); return; } ... startClet();`
   所以校验不通过时**正文 `startClet()` 根本不会调用**。
   用 `so_override` 在解析期改写 PLT 槽（不改代码页）：`verify→1`、`isRunningMemoryHack→0`、
   `isRooted→0`、`jWD_GetIsTerminateIfCracked→0`、`nativeFinish` 空实现。配置 `skip_drm`（默认 1）。
   **注意**：`Protection::initialize` 不能架空，否则 `nativeStartClet` 永久等待。
4. **目录 open 语义**：引擎用 `open(dir, O_RDONLY)` 探测数据目录，Horizon 拒绝打开目录 → 资源一个不加载。
   `shim_open` 失败时 `stat` 是目录就返回一个真实 fd（`<root>/..dir.stub`）。
5. **`system("ps > …")`**：反作弊扫描进程列表。返回 -1 时文件不存在 → 判定"无法验证" → 弹窗。
   `shim_system` 现在按 `ps > path` 生成一份只含本进程的列表（需要 `mkdir_p` 建父目录）。
6. **`getUserDir()` 必须以 `/` 结尾**：引擎用 `"%s%s/temp"` 拼接，缺斜杠会得到 `savecom.com2us…`。
7. **`generateHash([B,String)[B` 必须返回真字节数组**（16B），`getMaxMemory` 返回 512MB。
   未实现时兜底返回占位对象，引擎按数组读长度会取到野值。
8. **诊断自伤**：帧循环里每 600 帧 `malloc(512MB)` 探测，会把 newlib 的 break 一路推到上限，
   制造出"3GB 内存耗尽"的假象。已改为只读 `sbrk(0)` + 分配计数。
9. JNI 日志增加 `__builtin_return_address(1)`，能穿过 `_JNIEnv::Call*Method` 模板定位真实调用者；
   音频心跳带 `jni_last_method()` 作为现场快照。

当前状态：启动序列全通 → `startClet` 执行 → 加载 `UI_TITLEMAIN_01/02.png`、`font.fnt`、`Default.png` →
帧循环持续（约 1500 fps，无 vsync）但画面仍是黑的。下一步：`Default.png` 打开之后引擎停在
纹理上传/状态机，需查 `SGL_Texture::FromResource` 或 `gmaeloader` 的等待条件。

## 真机崩溃定位 + 黑屏终结（07:30 这一轮）

崩溃报告（`logs/20261030-072730/crash_report_0_*`）给出：
`nativeProcess → TM_Run → StartCletProcess → FONT_Load → RES_LoadToPool → free()`，
PC 落在 NRO 的 `_free_r+0x2c`，`free(-2)`。原因是引擎在 GetResource 失败后仍把错误码当指针释放
（引擎自身的错误路径 bug），所以真正要修的是**让资源读取成功**。

顺着查出的三个真 bug：

1. **`shim_mmap` 不读文件内容**：只 `memalign` 一块零内存。引擎靠 mmap 解析资源头，全零 = 非法包。
   现在按 `(fd, off, len)` 真正 `read()` 进来（并保存/恢复文件偏移）。
2. **`struct stat` 布局不兼容**：`shim_stat` 直接把 newlib 的 struct 写进引擎缓冲区，而引擎按 **bionic**
   布局在偏移 `0x30` 读 `st_size` → **所有文件都被当成 0 字节** → `ResourceManager::Add` 返回 `size=-1`
   → `calloc(-1)` 失败 → 崩。新增 `to_bionic_stat()`，stat/fstat/lstat 全部按 bionic 128 字节布局填写。
3. `so_set_overrides` 只能存一张表，第二张会覆盖第一张 → 改成可叠加（最多 8 张）。

验证（Eden）：8 个资源全部带正确大小注册（`UI_TITLEMAIN_01.png` 659873、`font.fnt` 3960、
`game.dat` 46884、`memorytext_en.dat` 167131…），`mmap` 读到真实字节数，引擎开始 `requestRender()`，
**帧缓冲中心像素从 `00000000` 变成 `fffefcff` —— 标题画面真的画出来了**。堆稳定 189MB/3248MB。

诊断工具补强：`ResourceManager::Add` / `FindInformation` 的 PLT 覆盖日志（`res:` 前缀）、
帧循环里 `glReadPixels` 读中心像素（`gl:` 前缀，用来区分“黑屏”和“没画”）。

## 频闪修复 + JNI 槽位错位（10/30 晚 ~ 10/31）

**频闪**：根因是每轮循环无条件 `egl_swap()`。引擎 300k 帧/秒里只在 119 次里真正画过，
双缓冲就在"画好的"和"空白"之间来回切。Android 是 `RENDERMODE_WHEN_DIRTY`：
`requestRender()` 才呈现一帧。现在 `jni_take_render_request()` 只在那时 swap，并把循环
限到 60 Hz（`svcSleepThread`）。修完帧缓冲像素从跳变变成恒定。

|---|---|---|

| CallBooleanMethodA | 39 | **38** |
| CallIntMethodA | 51 | **50** |
| CallVoidMethodA | 63 | **62** |
| CallStaticObjectMethodA | 86 | **115** |

## 加载停摆的真正根因：shim_path 返回原指针导致 open 用未初始化栈

**症状**：标题画面出现但加载进度条不动、`i_pack.dat` 创建失败。
**根因**：`shim_path()` 对已经是设备路径的字符串（`sdmc:/...`）**返回入参指针而不是写进 buf**，
而所有调用点都忽略返回值直接 `open(buf)` → **用到未初始化栈**。日志里的
`fs: open(P5ÐÇi, 0x0)` 和 `fs: open(, 0x241)` 就是这个。
**修复**：`shim_path_resolve()` 里 `if (p != buf) snprintf(buf, ..., p)`，保证 buf 永远是最终路径。

修完立刻见效：`i_pack.dat`(2.4MB)、`i_tile.dat`、`i_mapfeature.dat`、`eventdata.dat`
全部生成，`startClet` 从 13s 降到 267ms，标题画面完整出现（SETTINGS / START / MORE GAMES + Hive 标）。

## 观测方法论的教训

在**帧开头**读 `glReadPixels` 拿到的是上一帧残留，害我以为开屏动画冻住了整整两轮。
正确做法：在 `jni_take_render_request() > 0` 的 present 分支里、`egl_swap` 之前读。

`glScissor` 原点在**左下**，而从引擎/截图得到的坐标是**左上**，绘制时必须 `y = H - y`。

## 输入：手柄 → 触摸

- 真实入口 `handleCletEvent_MV(action, x, y, id, pointerCount)`：1=按下 2=移动 3=抬起，
  坐标打包 `(x<<16)|y`，`pointerCount` 直接写进触摸计数全局 `0x6e456c`。抬起必须传 0。
- 按下和抬起**不能在同一个 nativeProcess 里**，否则游戏看不到"按住"。现在跨 8 帧。
- 两套模式：聚焦框（左右切换菜单项，A 确认）与自由光标（右摇杆瞄准）。
  `input.c` 的 `focus[]` 是百分比坐标+尺寸，标题画面三个按钮：SETTINGS(20.5,77,24x6)、
  START(50,84,33x13)、MORE GAMES(78,77,24x6)。**START 是更大的按钮且更靠下**。
- 叠加层默认关闭（`[input] overlay = 0`）：真机以触摸屏为主，先验证能玩再调操控。

## 真机黑屏崩溃：finalize 之前读 load_virtbase

崩溃报告（`01707395737_0100d9f01d474000.log`）：`Data Abort at 0x1eaf13e56c`
= `virt(0x1eaea5a000) + 0x6e456c`。日志停在 `input: looking up handleCletEvent_MV` 之后。
原因：`input_bind()` 在 `so_finalize()` **之前**运行，此时 `load_virtbase` 只是"将来要映射到的地址"，
内存还不存在；我却在那里读引擎的触摸计数全局 → 真机数据异常。Eden 恰好那块有页所以没暴露。
修复：新增 `input_set_base()`，在 `so_finalize()` 之后调用，两段日志分别打印"probe"和"readable"，
这样万一还崩，日志能明确指出是哪一步。

Eden 侧输入配置（`%APPDATA%\eden\config\qt-config.ini`）：
- `[Controls] mouse_enabled` 原为 false → 鼠标点击不会变成触摸事件，改成 **true** 即可用鼠标点游戏。
- 默认键位：A=**C**、B=**X**、左摇杆=**WASD**、右摇杆=**IJKL**（`analog_from_button`）。
- 摇杆是电平不是边沿，聚焦列表必须做锁存（`stick_latch`），否则按住左会每帧走一遍列表。

## 触摸终于生效：引擎的输入空间是 480x320，不是屏幕像素

**决定性发现**：`handleCletEvent(code, packed)` 内部会用
`SGL_GetScreenWidth()/480` 和 `SGL_GetScreenHeight()/320` 缩放坐标，然后交给
`GLOBAL_SetPointer`（它只吃一个 0x18 字节结构体指针，x0 是全局对象、x1 是源）。

即：**输入空间固定 480x320**，引擎再放大到自己的 viewport（实测 1137x640，和我们渲染的
1920x1080 不同）。代入后 W/H 抵消：

    x_engine = screen_x * 480 / view_w        (1920 宽 → /4)
    y_engine = screen_y * 320 / view_h        (1080 高 → *8/27)

之前一直传屏幕像素 → y=918 在 320 空间里完全越界 → UI 认为点在屏幕外，什么都不发生。
日志里 `press at (960,907), touch count 1` 一切正常，所以看起来"输入通了但没反应"。

修好后的验证（Eden，tap_test 自动点）：
- 点 SETTINGS(screen 480,896 → engine 120,265) → **设置界面打开**（ON/OFF/SAVE/LOAD/语言）
- 点 START(screen 960,918 → engine 240,272) → **弹出付费内容 YES/NO 确认框**，资源 71→137

其他已确认：
- 抬起要发 `count=1`（得 0x18 单指抬起），再补一发 `count=0` 把触摸计数归零。
- `SGL_GetScreenWidth` 只有 `nativeStartClet` 之后才有值，启动早期读到 0 属正常。
- 焦点框几何按 1920x1080 实测：SETTINGS 432x75 @ (480,901)、START 510x81 @ (960,919)、
  MORE GAMES 375x75 @ (1417,901)。START 更大、更靠下。

## 真机进度条不走：包名子目录不存在，所有创建失败

真机日志（build 22:25）里路径是对的，但：
```
fs: open(.../save/com.com2us.../i_pack.dat, 0x241) -> -1 (failed)
fs: CS_fsOpen('i_pack.dat', mode 4) -> -12
```
真机 `save/` 下面**没有包名子目录**（`save/com.com2us.inotia4.normal.../`），所以
`O_CREAT` 全部 ENOENT。Eden 里这个目录恰好被早期 `shim_system` 的 ps 模拟 mkdir_p 建出来过，
所以一直没暴露——典型的"只有真机才复现"。

**修复**：`libc_shim.c` 里把 `mkdir_p` 提前，加 `ensure_parent()`：
- `shim_open`：失败且带 `O_CREAT` 时 → 建父目录 → 重试一次
- `shim_fopen`：失败且 mode 含 `w/a/+` 时 → 建父目录 → 重试一次

验证：删掉 Eden 的包名目录后重跑，目录和全部运行时文件（appinfo/envinfo/eventdata/
i_mapfeature/i_pack/i_tile）都正常生成，`res: 137 / fs: 305` 与之前一致。

经验：**凡是"引擎要写文件到 Android 上已存在的目录"的地方，都要假设该目录在卡上不存在。**
