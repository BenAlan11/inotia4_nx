# 11/03 存档功能修复（跨进程读不出 / 角色丢失）

## 现象
写完存档、退出游戏再进，槽位文件还在但读不出来（错误 00），角色像是没了。
同一次运行内存档读写正常 —— 这是关键线索：写它的进程自己能解，换个进程就废。

## 根因（已用哈希指纹证实）
存档链路（libgame.so）：

```
SAVE_SaveData(slot, data, len)
  key    = HubSave_GetKey()                    // 0x1229c8
  folder = hex(CC_MD5(key))                    // HubSave_GetFolderName 0x122ac8
  path   = "<folder>/save%d.dat"               // HubSave_MakeFullName
  file   = ENCRYPT_Process2(data, len, 0, key) // 0x1375a0，密钥当 x3 传进去
```

而 `CC_MD5`(0x211d14) 实际是 `b 0x2969c0` → 二级 PLT 桩 → 走 Java 侧 MD5，
壳里就是我们 `jni_fake` 的 `generateHash`（FNV-1a）。
于是槽位目录名 = `hex(generateHash(key))`。

**实测目录名 `83039d73b00f651483039d73b00f6514` 恰好等于 `generateHash("")` 的十六进制**
（该值 8 字节一循环，正是假哈希的特征，真 MD5 不会这样）→ **`HubSave_GetKey()` 返回空串**。

空串的后果在 `ENCRYPT_Process2` 里：
```asm
sdiv w14, w0, w21     ; w21 = strlen(key) = 0 → 除以零，AArch64 返回 0
msub w14, w14, w21, w0 ; → w14 = w0（整数，不再取模）
ldrb w14, [x20, w14]   ; 从密钥缓冲往后读 nonce+i（0~3000）字节
```
即 key 索引从 0xcf 起一直涨到 3000+，**异或掩码来自 HubSave_key 之后的 BSS 垃圾**。
BSS 内容每个进程不同（指针、计数、堆地址）→ 掩码不同 → 跨进程必然解不开。
同进程内 BSS 不变，所以当场读写是好的。

之前的 `save: seeded HubSave_key (64 bytes)` 补丁为什么没用：
`HubSave_LoadKey` 走了 "atoi(deviceId) < 1" 分支，`strb wzr,[x19]` 把 key[0] 写成 0，
`strlen` 恒为 0，种子字节只被当成"越界区里的随机数据"，从来没被当作密钥字符串用过。

## 修法（src/main.c）
1. **`HubSave_GetKey` 覆写 → 固定字符串** `inotia4-switch-save-v1`（可写静态缓冲）。
   一次覆盖两个用途：目录名（generateHash 的输入）和加密密钥。
   内部仍先调真实 GetKey()，保证 `HubSave_keyType` 等副作用不变。
2. **`SAVE_SaveDataAsNameAndKey` / `SAVE_LoadDataAsNameAndKey` 覆写**：第四参数强制同一密钥，
   并打日志：`save: write '<path>' N bytes, engine key '<空/内容>'` / `save: read ...`。
   写完后会用引擎自己的 `ENCRYPT_Process2(mode=1)` 对副本做**回读校验**：
   `save: round-trip ok/FAILED (N bytes)` —— 当场就能看到密钥是否对称。
3. **`ENCRYPT_Process2` 兜底**：任何调用点传空/NULL 密钥，都替换成固定密钥，
   避免再有 "除以零 + 越界读" 的路径。
4. 三张表统一走 `so_set_overrides`（GOT 覆写，先于 so_resolve 安装）。

预期（**实测已修正，见下**）：槽位目录**不变**，仍是 `83039d73...6514`。
因为目录名 hash 的输入不是存档密钥，而是"账号 id"（`getAppProperty` 返回空），
所以 key 变了目录不变。旧目录里的旧存档**无法恢复**（掩码来自当时的 BSS 垃圾）。

## 验证方法与实测结果（13:00 运行）
日志实证（13:00 那次）：
```
save: read '830.../save0.dat', engine key 'inotia4-switch-save-v1'     ← 成功
save: read FAILED '830.../save1.dat'                                   ← 文件不存在
save: read FAILED '830.../save2.dat'                                   ← 旧文件，解不开
save: read FAILED '830...6514A/thpcheckslot3.dat'  → UI_SetPopupProcessInfo(4,0)
```
注意 `engine key 'inotia4-switch-save-v1'`：说明引擎自己的 `HubSave_GetKey`
确实返回了我们钉的串（覆写生效），内部调用链仍有第二路带 `'(empty)'` 的
（CWrapperKernel 的槽位校验），也被 wrapper 强制成同一把钥匙。

离线校验（决定性）：用固定密钥解 3169 字节文件 = `len-3` 字节明文 + `[sum_c] 密文和`、
`[nonce]`、`[sum_p] 明文和`；解出后再算两个校验和：
- `save0.dat`（新写）：两个和都对，明文 1584/3166 为零 → 正常存档
- `save2.dat`（旧）：密文和对、明文和错 → 空密钥时代产物
- `thpcheckslot1.dat`（新）：两个和都对，明文 `2|0000000|99|99|99|99|99|END|`

## 槽 2/3 的真相与固化（13:0x）
- 槽 3 = 12:31 的旧 `save2.dat`+`thpcheckslot3.dat` 还在 → 点它解密失败 → 错误弹框；
  **弹框占住输入树，下一次点别的槽（哪怕空槽）会落到陈旧 root**，
  所以"点空槽 2 却像在加载 3 槽、黑屏"。已把两个文件移到 `save_backup/orphan_1231/`。
- 槽 2 根本没有 `save1.dat`，点它是新建角色（正常）。
- 新增自愈 `quarantine_stale_saves()`（main.c，nativeStart 之前调用）：
  遍历 `<save>/<pkg>/*/` 下 `save*.dat` / `thpcheckslot*.dat`，用固定密钥解一次，
  解不开就改名 `*.dat.bad`（**不删**），0 字节的 save 文件也算坏的。
  这样"占位但损坏"变成"空槽"，不会再劫持输入树。
  → 只要判据（解密返回 1）成立，就不会误伤好文件；已用真实文件离线验证过判据。

## 工具经验
- `tools/plt.py` 只解主 PLT 区；0x296xxx 还有一片二级桩（GOT 槽 0x2a6xxx，**无 rela**，
  由运行时填表），`CC_MD5` 就跳这里 → 实际落到 Java 侧。

- 查 "掩码/密钥" 类问题的一条捷径：**用假哈希反推**。目录名是 `hex(hash(key))` 时，
  对候选 key 直接算 FNV 比对，一次就能确认 key 是什么（这里是空串）。
- 0x28b5d0 之后不是 .text，`disas_at.py` 报的 "nearest export" 会误导。

## 13:2x 「玩过一局后回主菜单，点开始游戏进不了存档页」（已修）

现象：进存档 → 游戏内设置 → 回主菜单 → 点 START 没反应。
日志（13:18 那次）末尾连续 30+ 次：
```
klog: arg1: config arg2: HUB_LOGIN_INFO
ui: prompt 1 type 2 text ''
ui: prompt 1 skipped, bridging straight to the save list
```
控件树 root 不再变化 → 引擎在原地重试，界面没动静。

根因：桥接用了 `static int bridged_once`，**进程内只允许一次**，开机那次已用掉。
所以第二次按 START 时提示被吞、桥接不执行，引擎等不到结果就死循环重试。
（当初做成一次性是为了防止"每次重试都推一次存档页"导致画面来回弹。）

修法：把 `bridged_once` 换成可重装填的 `bridge_armed`，
在 **`Title_ButtonExe`（0x1f1188，标题页 START，函数体只有 `STATE_Set(4)`）**
覆写里重新 arm。GOT 槽 0x29fa70 可覆写；引擎后续重试不会重新 arm，
所以"来回弹"不会复现。

日志标记：`ui: title START pressed, save-list bridge armed`。

## 14:2x 「删除存档」与「回主菜单后再点开始游戏」双双修好（用户实测通过）

### 删除存档（原来点了"是"没反应）
两个独立 bug 叠在一起：

1. **引擎自己的 unlink 一直失败**。引擎删档时把 `/switch/inotia4/save/...`
   （丢了 `sdmc:` 前缀的卡路径）传给 `unlink()`；`shim_path()` 对"没匹配任何前缀的
   绝对路径"是**原样返回指针**，调用点却继续用自己未初始化的 `buf` →
   日志里就是 `fs: unlink() -> -1`（路径是空的）。
   修法：`shim_path()` 增加 `/switch/...` → `sdmc:/switch/...`；
   `shim_unlink/remove/mkdir/rmdir/rename` 全部改用 `shim_path_resolve()`
   （这个函数保证结果物化进 buf）。
2. **我自己的"补删"把进程搞崩**。在触摸回调里（后来改到主循环）直接 `remove()`
   引擎正打开着的 `save1.dat`，删完那一行日志后进程立刻消失（Eden 侧日志停在
   一条 svc_debug_string，无异常记录）。最终方案：**撤掉手工删档**，只保留
   垃圾桶识别与日志，删除交给引擎自己做（它才知道要不要刷新列表/写 checkslot）。

教训：**不要在引擎的游戏循环里替它动它正在使用的文件**；定位"文件操作失败"优先看
shim 的路径解析，`shim_path` 返回值必须走 `shim_path_resolve` 落到 buf。

日志判据：`fs: unlink(sdmc:/.../saveN.dat) -> 0`（以前是 `-> -1`）。

### 回主菜单后 START 进不去存档页
`ui: prompt 1 skipped, bridging straight to the save list` 连续刷 30+ 次而界面不动：
桥接用的 `static int bridged_once` **进程内只允许一次**，开机那次已用掉。
修法：改成可重装填的 `bridge_armed`，在 `STATE_Set(4)` 覆写里 arm
（`Title_ButtonExe` 只是 `STATE_Set(4)`，但实测该导出没被调用，挂它无效）。
日志判据：`ui: STATE_Set(4)` + `ui: title START pressed, save-list bridge armed`。
