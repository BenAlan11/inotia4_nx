## 19:46 卡死根因（最终结论）—— 是诊断日志调了引擎的文本度量

用户每次都是「点存档、行变红后卡死」。栈固定为：
```
TM_Run → MainProcess → GAMESTATE_DrawPlay → UIPlayPorting_Draw
       → UIPorting_DrawNumber+0x68 →(回落地址) nx_grpx_draw_string+0x214
```
**定位方法（以后照抄）**：
1. `lr` 是 NRO 里的地址，NRO 基址 = `0x80eb3000`（由日志 `patch: ExeMercury -> 0x80ec4950`
   减 ELF 里 `mercury_none` 的 `0x11950` 得出）；
2. `0x80ec90e4 - 0x80eb3000 = 0x160e4`，用 `objdump -d` 看该处前一条指令即可：
   `0x160d8..0x160e0` = `grpx_measure()` 里的 `blr x8`（引擎虚函数 `SGL_GetTextSize`），
   `0x160e4` 正是它的返回地址。

所以卡死**不是 FreeType、不是字号、不是缓存**，是我们在 `nx_grpx_draw_string`
的日志块里调用 `grpx_measure()`（= 引擎自己的 `SGL_GetTextSize` 虚函数），
那条路走 Android 字体度量，在本 shell 里永不返回。游戏内 HUD 画第一个数字就撞上。

修法：删掉日志里的引擎度量调用（引擎宽度只是打印来对比），并删除
`grpx_measure()` / `grpx_group()`。**端口现在完全不调用引擎的文本度量**。

教训（重要）：
- 诊断日志不许调用引擎函数，尤其在每帧热路径上（数字每帧都画）；
- 字号钳制（6..96）保留但**不是**这次的原因，别把它当解药；
- 用 `lr` 反查比读栈帧可靠得多（-O2 下我们没有 frame pointer，fp 走栈会漏掉自己的帧）。

## 20:35 文字"应在红框内" —— 文本控件的 y 是**基线**不是顶端

用户红框量出来的证据（截图 1139x454，用左侧 75x75 按钮行做标尺：
按钮 engine y=155/232/309，间距 77 → 截图缩放 ≈1.57，y0≈-182）：

| 量到的 | 截图坐标 | 换算成 engine |
|---|---|---|
| 红框 | y 32..87 | 136..171（高 35，中心 153.6）|
| 白字墨迹 | y 66..92 | 158..174（中心 171）|

也就是说文字整体比"应该在的位置"低约 12~18px ≈ **一个 ascent**。
原因：`X_TEXTCTRL_DrawTextControl` 把 y 传给 `GRPX_DrawStringImageEx` 作为
字符串图像的锚点（行盒中心/基线），我一直把它当行首顶端用。

`text_face_ascent()`，取 FT face 的 ascender）。px=20 时约 -18px，
文字墨迹变成 144..162，中心 153 —— 和红框中心 153.6 对上。
配置开关 `textctrl_baseline`（默认 1，改 0 回到旧行为）。

注意：`p_abs_rect(ctrl)` 对这些文本控件返回 0,0 0x0（不在树里 / 没有 rect），
想用控件矩形做对齐这条路走不通，最后是用"基线"语义解决的。

## 22:10 黑条身份查清 —— 引擎画的高亮条，文字应"居中"于锚点

探针一次性拿到（这是决定性证据）：
```
bar: quad 80,152-1057,172  tex 31  col 0.00 0.00 0.00 0.60  blend 1
```
即：黑色、alpha 0.60、矩形 (80,152)-(1057,172)、高 20、**中心 y=162**，
而 162 正好是 `X_TEXTCTRL_DrawTextControl` 交给我们的 y。

结论：引擎把 y 当作**字符串图像的中心**（它自己的图也是居中贴），
我们按"顶端"画就整体低了半个行高（约 8~10px），字下缘露在条外。
