## 13:0x A/B 逻辑绑定 + 光环探针（未验证，等用户实测）

### 1. A/B 分发给「层」而不是固定按键

原来只有 `!hud`（菜单页）时 A/B 才走 `menu_key_press`；在图上 A 固定打攻击盘、
B 固定 `pad_release`。所以「确认/是」「取消/否/返回」在游戏里根本到不了。

新增 `ab_layer()`（`src/input.c`），每帧决定 A/B 归谁：

| 层 | 判定 | A | B |
|---|---|---|---|
| `AB_POPUP` | `UIPopupMsg` 主控件/基控件非空 | `UIPopupMsg_ButtonOKExe()` | `UIPopupMsg_ButtonCancelExe()`；**没有取消按钮时退化成 OK**（引擎 `UIPopupMsg_Event` 0x15e8dc 就是这么做的） |
| `AB_SCENE` | `POPUPSTATE_Exist()` | `menu_key_press(1)`（键表 tbl[4]） | `menu_key_press(0)`（tbl[16]） |
| `AB_MAP` | `input_hud_present()` | 攻击盘 press/release | 停止走路（保留原行为） |
| `AB_MENU` | 其余 | `menu_key_press(1)` | `menu_key_press(0)` |

- 引擎里 `UIPopupMsg` **不是 scene**：它靠 `handleCletEvent(code=3)` →
  `UIPopupMsg_Event` 读「当前键」再调 `ButtonOKExe/ButtonCancelExe`。
  移植不发按键事件，所以「连接出错。请稍后重试。确认」只能靠点屏幕，A/B 全无反应。
  直接调两个 Exe 回调 = 按钮松开时引擎自己做的事，且弹窗在回调里自删。
- 全局（反汇编 `UIPopupMsg_Get*Control` 得到）：
  `0x2b8d78` 基控件、`0x2b8d80` 主控件、`0x2b8d98` OK 按钮、`0x2b8da0` 取消按钮。
  基控件在任一按钮生效时被删并清零，所以「非空」就是「弹窗还在」。
- `POPUPSTATE_Exist()` = `ArrayStack_GetTop(*(0x29f530)) != 0`；
  `POPUPSTATE_Push` 只被 `UI_PopupProcessCreate` 调用，**play 场景不 push**，
  所以它正好等于「上面盖了一个 UI 弹层（角色/背包/商店/系统菜单…）」。
- 弹窗/弹层是模态：这一帧不驱动摇杆、不响应 +/-（否则地图还在底下动）。
- 每层切换打一行 `input: A/B now talk to the <层>`；弹窗按键打
  `input: message box OK/cancel -> ...`。

### 2. 金色光环：先装探针，别再猜

### 2. 根因：`0x29eb90` 是「槽的地址」，不是函数指针
`handleCletEvent` 0x169880 处是：
```

ldr x8,[x9]         ; x8 = 函数

```
旧代码把 `*(0x29eb90)` 当函数直接调 —— 那是一个数据地址。所以 B 在任何页面
（包括菜单）都不可能生效。现在改成 `*(*(0x29eb90))`，并把日志改成
`input: scene OK/back key %d -> handler %p`。

### B 不返回的真正原因（读反汇编定案，比「少解一层指针」更本质）
`POPUPSTATE_Event`(0x1bf4d0, 100B)：
```
ArrayStack_GetTop(*(0x29f530)) -> state
ldr x8,[state,#0x38] ; 页面自己的事件回调
blr x8
```
即每个 UI 弹层把「按了返回键」的处理放在**栈顶 popup state 的 +0x38**，
不是放在 `0x29eb90` 的场景 handler 里。

`handleCletEvent` 的按键分支（0x1696e8 起，POPUPSTATE_Exist 为真时）：
- code 2/3 都先 `KEY_SwaptoAndroid` + `KEY_SetCode` + 置 padflagB
- 然后 `ldrb w9,[x21]`（x21 = *(0x29ecb0)，由 `KEY_SetActive()` 置 1）为 0 就直接 return
- 再按 `*(0x29dbf0)` 决定 `UIPopupMsg_Event` 还是 `POPUPSTATE_Event(code,key,count)`

我们的 `menu_key_press()` 绕过了整条链，只调 `0x29eb90` 的 handler，
**从来没调用过 POPUPSTATE_Event**，所以页面上的 × 永远收不到「返回」。

下一版的正确实现（不要再用 menu_key_press 打补丁）：
1. 绑定 `handleCletEvent`、`KEY_SetActive`
2. A：`clet(2, tbl[4], 1); clet(3, tbl[4], 1)`
   B：`clet(2, tbl[16], 1); clet(3, tbl[16], 1)`（tbl[16] 实测 = -16）
3. 发之前 `KEY_SetActive()`（否则 0x169730 直接 return）
4. 这条链同时覆盖消息框（UIPopupMsg_Event code 3 -> ButtonOKExe/ButtonCancelExe）
   和 UI 弹层，可以把 popup_press / menu_key_press 两条路径都替掉

⚠️ 不要再引入移动中的逐帧大截图（会卡渲染）；要截图就让用户直接发一张
肉眼可见光环的图。

## 22:26 真凶：GRPX_DrawPartFlip 包装少了一个参数（不是 wrap_extra，也不是本轮改动）

用户补充描述：右边那列本应是 `>`、和左边灰色 `<` 平行；有能力点金色，

反汇编实锤：
- `GRPX_DrawPartFlip`(0x121e50) 是 **8 参数**函数。调用点明确设 w7：
  `0x144454 mov w7,#1`、`0x14f198 mov w7,wzr`、`0x15434c mov w7,wzr`。

- 我们的 `nx_grpx_draw_part_flip()` 只声明 7 个参数，转发时 x7 是调用时的
  残留垃圾 → 箭头没翻成 `>`，Y scale 还可能为负导致整列上下翻转/位移。
- `GRPX_DrawPartEx` / `GRPX_DrawPartFlipEx` 没被 override，参数完整，
  所以只有走 Flip 的这一批贴图错，和观察一致。

**修复**（main.c）：函数指针与 wrapper 都加第 8 参数 `long flip`，
`grpx_draw_part_flip_real(h,x,y,rect,mode,p5,p6,flip)` 原样转发。
绑定处是 `(void *)` 强转，不需要改。

⚠️ 教训：给引擎函数写 passthrough wrapper 前，必须反汇编调用点数清
