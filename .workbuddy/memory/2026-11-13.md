## 设置页手柄交互全部重做（用户要求废除自己先前设定的那一套）
用户原话：「废除现有我加的设置页的几个操作设定（角色加点，技能加点，背包物品选取等），
你去网上找找其他游戏是怎么用手柄实现设置页这些交互的吧，比如塞尔达传说之类的，
由你设计一套操作逻辑」；随后澄清「我说的修好是指快捷按钮，攻击移动那些，
设置页的我设定的全部废除」。

**保留（不许动）**：六个快捷槽布局与 RT+X/Y/A/B、十字键左右触发左侧两槽、R 换页、
Y 攻击/地图交互、A 剧情对话推进（`ui_dialog_button`）、摇杆移动、HUD 映射、
标题/存档/职业三个前置页面的手柄入口（否则没法用手柄进游戏）。
**废除**：NAV_TOP/NAV_BODY/NAV_STAT 三级模式、角色加点模式（STAT_ENTER / STAT_PLUS /
STAT_MINUS / nav_stat_point / nav_stat_hold）、技能/物品页特化分类 `nav_classify()`、
`NAV_K_ACTION` 优先、两段职业确认、L/R 切页签后还要 A 进入内容、形状高亮按 kind 推导。

### 调研结论（WebSearch）
- 塞尔达 BOTW：左摇杆在网格里选格；右摇杆切分类页签/翻页（按住连翻）；
  A 确认、B 返回、X = Hold 批量拿取（最多 5）、Y = 背包内整理；L/R 换大类。
  Medium/Prototypr 的 UX 批评指出「多页时右摇杆既翻页又切页签」是痛点 → 新方案把
  切页签固定给 L/R + 右摇杆轻拨，不做翻页歧义。
- 原神：十字键选菜单项、LB/RB 切功能模块、L1+面键组合；NGA 评测明确建议
  「项目选择务必用十字键，抛弃左摇杆」「用 L/RB 切模块」。
- Xbox Accessibility XAG 112：线性列表循环、2D 网格方向键空间移动且**边缘停止**、
  每个屏幕都要有持续返回路径。
- 通用菜单导航规范：焦点困在最上层屏幕（focus trap）、关闭后恢复到打开它的控件
  （restore-to-opener）、只保留一个高亮、覆盖面板 inert、按住连发、默认焦点落在
  最高频动作（Game Menu Design / Game UI / menu-navigation skill）。

### 新方案（一套规则覆盖所有设置页，无任何页面特化）
- 控件树里最上层可见面板的**所有可点控件 = 唯一焦点集合**（遮挡过滤 + proc 白名单保留，
  它们属于底层设施，不是操作设定）。
- 十字键 / 左摇杆：按中心最近做空间移动，离轴距离 ×3 加权；网格边缘停止；
  按住 14 帧后每 4 帧连发。
- A：**永远只是 tap 当前焦点**。加点 +、技能格、物品格、弹框按钮全部同一条路径。
- B：退一层；用页面控件列表指纹判断弹框是否关闭，关闭后焦点回到打开它的那个控件
  （`nav_saved_*`）。
- L / R / 右摇杆轻拨：直接切页签（tap 目标 tab），不再有「页签栏层级」和 A 进入内容。
- X / Y 在菜单里完全不用，留给游戏内。
- 默认焦点：标题/职业页落在「开始游戏」，其余落在可见层第一个控件。

### 实施
- `src/input.c`：整段替换旧状态机（16137 B → 12496 B），新状态只有
  `nav_tab / nav_idx / nav_dirty / nav_repeat_* / nav_saved_*`。
- `src/main.c`：删除 `nav_classify()` 整个函数与调用、`nav_stat_mode` 变量，
  `input_set_nav` 的 stat_mode 实参改 0（签名保留以少改调用点）。
- `src/input.h`：删除 `NAV_K_STAT_*` / `NAV_K_ACTION` 枚举，更新注释。

## 20:2x 页签切换修复 + 去掉金色强调框
用户反馈：「页签切换有点问题，有时往右切换了往左切换不了，有时卡住，还有我看到
有的地方之前做的金色强调框有保留，这个能去掉吗」。

**三个根因，都从代码/日志坐实**：
1. `input_set_nav(present=0)` 会把内部 `nav_tab` 索引归零。切页签后引擎重建页面，
   日志里出现 `nav: page gone kind 1 (6 tabs, 0 controls...)`（连续 >=8 帧无控件，
   `nav_miss` 用尽才真正调用 `input_set_nav(0)`），于是游标归零 → 往右切完往左会
   跳到别的页甚至看起来没反应。
2. `input_tap_at()` 每次直接 `tap_frames = 8`，覆盖正在进行的 8 帧 tap 的 UP 事件。
   快速连按 L/R 会让引擎留着一根"按下未抬起"的手指 → 卡住。
3. `nav_gold_cursor()` 调用仍在渲染循环里（和 `cfg.overlay` 无关，overlay=0 也画），
   所以设置页/前置页面仍能看到金色形状框。

**修法**：
- 页签游标从"数组索引"改成"上次 tap 的 tab 中心 x 坐标" `nav_tab_x`：
  按方向找同侧最近的 tab，找不到就绕到另一端。天然对称，右→左必回原位，
  且不受页面重建影响。日志改为 `nav: tab right/left -> x=... (i/6)`。
- 合成 tap 加最多 4 个的队列：正在 tap 时新的 tap 排队，每个完整走完
  down(8)/move(4)/up(1)，不再互相覆盖。所有 tap 用户（页签、确认、返回）都受益。
- 切页签后置 `nav_grace = 20` 帧：重建空档仍由导航占住 L/R，避免 R 漏到
  `quick_swap_fire()`；`input_set_nav(present=1)` 立即清零，正常关菜单不受影响。
  `nav_update()` 在空档只保留 L/R，A/B/方向暂停；`input_nav_highlight()` 空档返回 0。
- 渲染循环里删掉 `nav_gold_cursor()` 调用；函数本体保留并标 `__attribute__((unused))`
  方便回退。`cfg.overlay` 的黄直角框是另一套调试绘制，overlay=0 本来就不画。

## 11-14 00:0x 滚动页诊断（用户提问）+ B 兜底
用户问「技能页因为是可滚动的页面，是否因为这个所以控件读取有问题？」

**结论：是，有两层**，证据来自控件树与代码：
1. 滚动视口 `ControlScroll_EventProc`(0x13e72c) 的树形如
   `194,151 374x394` → 子 `204,151 364x554`(0x130514)，**里面没有任何条目控件**。
   内容高度 554 > 视口 394，条目由 `nx_desc_text_scroll` 绘制回调（接管了
   `data+0xa0`）画出来，是字符串图/排版，不是 ControlObject。
   `nav_collect_items()` 只能读到视口外的固定按钮 → 滚动区域里的项目无法成为焦点。
2. 滚动位移来自 `input_take_drag_dy()`，而它只消费 `input_touch()`（真实触屏）
   累积的 `drag_acc`。手柄方向键/摇杆完全没有接进这条通道 → 手柄连滚动都做不到。
   `desc_scroll_tick()` 还要求 `input_drag_start()` 落在视口矩形内。

注：技能网格页（74x74 / 127x114 那些）条目是真实 `ControlItem_EventProc` 控件，
能正常读；出问题的是「说明/描述类可滚动页」。

**顺带修 B**（日志证明上轮承诺未兑现：`nav: B closes top panel` 计数 0，
`nav: B backs out` 2 次）。原因是任务/说明页的 `UIGameMenu_SubEvent` 直接子里
根本没有 ControlButton 关闭 ×。新增 `nav_opener_x/y + nav_opener_valid`：
A 时记住打开面板的那个控件，B 优先 tap 面板关闭 ×，找不到就**再 tap 一次来源
控件**（引擎把第二次点同一物品格当成关闭详情），再不行才页面级返回。
`nav_panel_closed` 两段式保留，第二次 B 仍退菜单。日志
`nav: B toggles opener at (...)`。切页签/进页面清 opener。
