## 00:0x 用户纠正「技能树本身也是可滚动的」→ 实施自由光标 + 手柄拖拽

与 `nav_cursor_tick(down)`、`input_nav_cursor(int*,int*)`（input.h 声明）。
- **last-device-wins**：右摇杆一动 → 光标模式；十字键一动 → 焦点模式。只画一个高亮。
- 右摇杆以 16px/帧移动自由光标，死区 0.18，屏幕内 clamp；进页面时光标在屏幕中心。
- **RT + 右摇杆** = 在光标处注入真实拖拽：`input_touch(0/1/2, ID_PAD, ...)`，

  技能树的 ControlScroll 事件链）。松开 RT 自动抬起；页面消失时也强制抬起。

  把光标移到滚动区域里。
- **A**：光标模式 → `input_tap_at(光标)`；焦点模式 → tap 当前焦点控件。
  0 控件页（纯滚动页）也允许光标点击（在 `!ready` 分支里单独处理）。
- 右摇杆**不再**切页签；页签只由 L/R 负责。
- `main.c` 新增 `nav_cursor_mark()`：深底 + 亮白细十字准星（18px），
  与焦点小箭头二选一显示。

## 13:2x 设置页消息框（确认 / 是-否）A/B 直接生效
用户截图：设置页里弹出黑底「保存成功 / 确认」框，反馈「(1/6)到(6/6)都会有，
按 A/B 无法直接确认或者是否，需要将光标移到相应位置」。

**根因**：`input.c:nav_update()` 的 A/B 分流写成
`if (!settings && (A|B) && (popup_on() || ui_confirm_button(...))) { ab_press(); return; }`，
注释还写死「Settings pages never had one and must not steal it」。这个假设错了：
日志 `ui: routing touch to the message box 0x... (was root 0x...)`（来自
`nx_TouchHandle_Event` 的 `popup_base_real()`）证明设置页确实会弹 UIPopupMsg。
于是 A 落到 `nav_tap(焦点控件)` 去点被框遮住的底层控件、B 落到逐层返回，
只能靠移光标去点确认。

**修法**（`nav_update` 开头，前置页面逻辑之前）：
- `if (popup_on()) { if (A|B) ab_press(A?1:0, AB_POPUP); return; }`
  —— 对所有页面生效；`popup_on()` 读引擎自己的 `POPUP_BASE`(vb+0x2b8d78) 指针，
  框关闭时被引擎清空，不会误判残留。A=确认/是，B=取消/否
  （`popup_press` 里 `use_ok = ok || !cnc`，单按钮框按 B 也走 OK；
  双按钮框按 B 调 `p_popup_cancel()`）。框期间其它按键全部冻结，焦点不会跑到框后。
- `ui_confirm_button()`（UI_PopupProcess 路障框，无 UIPopupMsg base）**仍只在
  前置页面启用**：设置页自身的 `UIGameMenu_SubEvent` 面板也带
  ControlScroll+ControlButton 结构，若放开会被误判成模态确认，破坏正常 A/B。
- `hud_update()` 已有 `if (input_nav_active()) return`，nav 不 active 时由它
  按 `ab_layer()==AB_POPUP` 走同一条 `ab_press()`，两条路径不会双触发。

## 17:2x 修复「从移植开始一直没声音」：音频链路从头到尾就没接通
用户「现在来修复游戏声音，目前为止一直没有声音」。**不是回归，是从未接通**。

### 三层断点（全部由反汇编 + 日志坐实，不是猜）
1. **引擎的 C 音频 API 全部转发到 Java，假层接不住**。
   `CS_mdaSoundCreate/Prepare/Play/Stop/Destroy/SetVolume`（0x24e268..0x24e46c）
   都只是薄壳，转 `jSoundCreate/jSoundPlay/...` → JNI →
   `com.com2us.wrapper.media.CSoundManager`。
   - `jSoundManagerInitialize`(0x2567d0) 是 **Java→native** 的初始化函数，
     Switch 上没人调它；它是唯一把 `soundPlay(IZ)Z` 的 jmethodID 写进
     `[so+0x6e4680]` 的地方。该全局恒 NULL → 日志里 24 次
     `j_CallBooleanMethodA got a bogus method id 0x0`，播放调用全被吞。
     方法名/签名从 .rodata 读出：0xaff78='soundPlay', 0xb5381='(IZ)Z'。
   - 假层实现的是 `soundLoad/createSound/playSound`，引擎真实名字是
     `soundCreate/soundPrepare/soundPlay`（0xb2cc8/0xb178e/0xaff78），
     名字对不上 → soundCreate 恒返回 0、soundPrepare 恒 false。
   - **PLT 桩 0x297650 = `_JNIEnv::CallBooleanMethod(...z)`（varargs）**，
     而 `env_table[38]` 接的是 `j_CallBooleanMethodA`（jvalue 数组）。
     现在 id=0 时 `read_jvalues` 因 `!args` 直接返回才没崩；一旦给
     soundCreate 返回非 0 id，下一次调用会把 id 当 jvalue* 读 → 数据中止。
     ⇒ **不能只补 method id**。
2. **audout mixer 一次都没跑**。旧日志 197 行 `audio: alive` 全是
   `audoutWaitPlayFinish` 的 R_FAILED 分支。timeout 传 `1000000` 是
   **1 毫秒**（libnx 单位是纳秒，注释却写「一秒」），线程每秒自旋千次，
   与 `audoutWaitPlayFinish` 开头的 `eventClear()` 抢释放信号。
   改成 33333333ns（≈33ms，一个 1024 帧 buffer 是 21.3ms）后立刻
   `audio: MIX 1024 frames`，且 `audio: alive` 归零。
3. **44.1kHz / 单声道资源**。全部 Ogg 是 44100Hz，SE 是 mono，audout 固定
   48000Hz 双声道。`decode_to_pcm` 本来按 `cfg.audio_freq` 重采样（碰巧也
   48000），改成按 `audoutGetSampleRate()`；BGM 原先直接把 44100 样本灌进
   48000 输出（会变调变快），`refill_bgm()` 新增流式线性重采样
   （`bgm_raw[4096*2]` → `bgm_buf[8192*2]` + 跨块相位 `bgm_phase`）。

### 修法：hook 引擎自己的 C API，绕开整个 JNI 层
- 新增 `src/audio_bridge.c/.h`，`main.c` 注册 `audio_overrides[]`（10 个
  `CS_mdaSound*` 符号），用 `so_set_overrides()` 在 `so_resolve()` 前替换
  PLT 槽（**放在 `if (cfg.skip_drm)` 之外**，与 DRM 无关）。
- `SOUNDSYSTEM_PlayBGM_IPHONE`(0x1d4a98) 反汇编证明 BGM 也走同一套：
  `CS_mdaSoundCreate(&h,"SOUND/BGM/%s",0,0,1)` → Prepare → `Play(h,1)` →
  `SetVolume(h,100)`；`w1=1` 就是 loop（普通 UI 音效传 0）。格式串在
  0xb406d = `SOUND/BGM/%s`。
- 路径 = `g_data_dir + "/resources/common/game_res/" + name`，与引擎 RES
  loader 的前缀一致，无需新配置键。BGM 名字前缀 `SOUND/BGM/` → 走
  `audio_bgm_load/play` 流式通道并返回合成 handle `0x40000000`；其余走
  `audio_sfx_load/play`，`slot_vol[]` 记 0..100 音量。
- `MAX_SFX` 96 → **256**（SE 目录实际 170 个文件，96 会让后面的屏静默）。
- `audio_init()` 现在检查并打印每个 `audoutAppendAudioOutBuffer` 的 rc
  和 `threadCreate` rc（以前全忽略，服务若拒收就永久静默且无错）。

## 17:5x 快捷键分配页「光标读不到 6 个快捷按钮」
用户截图：标题「请选择要设置的快捷键。」，左下 2 个 + 右侧 4 个圆形槽，
白色 `>` 焦点箭头却停在两个红圈之间的空隙。

**根因（两层，都在 `nav_scan()`）**：
1. `nav_is_actionable()` 白名单只有 `ControlButton_EventProc` /
   `ControlItem_EventProc` / `ControlSkill_EventProc`。这 6 个 80x80 槽用的是
   **`UIShortcutMenu_Shortcut_EventProc`**（`shortcut_proc`，main.c 3659），
   **故意**被排除——游戏内同 proc 的 HUD 快捷槽不能被焦点抢走，否则和摇杆/
   面键打架。
2. 该弹层是 `UI_SetPopupProcessInfo(1,9)` 压出来的，不是 `nav_page_kind_of()`
   认识的四种形状（SETTINGS/CLASS/SAVE/TITLE），所以 `nav_page_obj` 仍指向
   底下那层，遍历根本走不到弹层。日志佐证：弹窗打开后 `nav: page ...` 状态
   没有任何变化，items 仍是底层的 29 个（74x74 网格 / 125x55 按钮），
   一个 80x80 都没有；同时 `quick: assign page slot 0..5 ... -> 945,395 ...`
   证明 6 个槽确实在树里且已被搬到十字位置。

**修法**：`nav_collect_shortcut_slots()` 从 **整棵 root 树**（不依赖
`nav_page_obj`）按 `p_ctrl_proc(c) == shortcut_proc && 80x80 && id 不在 8..13`
收集——与 `hud_scan_node()` 区分「分配页槽 vs HUD 稳定 id 8..13」用的是
同一套判据。恰好 6 个时：清空 tabs/items，只把这 6 个 rect 作为焦点集合，
`kind = NAV_PAGE_SETTINGS` + `present = 1`（A=tap 焦点、B=关弹框、
`nav_ntabs=0` 让 L/R 自然失效）。focus tap 走 `input_tap_at`，而这 6 个 rect
早就在 `hud_quick_hit()` 白名单里（`input_set_quick_rects`），不需要改触摸层。
每次 `nav_scan()` 都从活树重收，关弹窗后下一个 4 帧 scan 就恢复原焦点集，
不等 30 帧的 HUD 对象缓存。
