# 2026-11-18

## 18:35 设置页背包标签停留后崩溃 —— 4 份报告同一指令，moving control 悬空

用户：实机在设置界面（背包标签页）待一会儿就「软件发生错误，已关闭」，崩了不止一次。
给了 5 份 crash report + 5 张崩溃瞬间截图。

### 报告读出来的事实
- 5 份里 **4 份 PC/LR 完全相同**：`libgame + 0x13e59c`，Data Abort，Address=0xa。
- 反汇编 0x13e590（`ControlItem_GetMoving`，导出 size 24）：
  ```
  0x13e598  bl 0x28d5b0      ; PLT -> ControlObject_GetData  (GOT 0x2a1898)
  0x13e59c  ldrb w0,[x0,#0xa] ; ← 崩：x0 == NULL
  ```
  X[17] 正好是 `ControlObject_GetData` 的地址（libgame+0x130e50），交叉印证。
- 调用者 ReturnAddress[00] = `libgame + 0x14a4cc`，落在 **UIEquip_Process**
  （0x14a4a0）里：
  ```
  ctrl = TouchHandle_GetMovingControl();      // GOT -> 0x2b2eb0
  if (!TouchHandle_IsControlEventMove()) ret;
  if (!ControlItem_GetMoving(ctrl)) { ... }    // ← 崩在这
  ```
- 结论：**触摸状态里的"正在拖动的控件"指向一个 data(+0x50) 已为 NULL 的控件**。
  触发场景：点背包格 → 「背包已满。」弹窗 → 点弹窗关闭（弹窗控件被销毁）→
  moving control 没被清 → 下一帧 UIEquip_Process 把它当 ControlItem 读 → 崩。
  日志里弹窗关闭那一帧正好是 `TouchHandle_Event ... (0 children) code 0018`
  之后第一帧。
- 第 5 份（01708651048）是**另一个点**：`libgame + 0x13357c`
  = `LINKEDLISTITEM_getData` 里 `ldr x0,[x0,#8]`，FAR=0。暂未处理。

### 工具
- 解析 PLT 桩 → 符号：脚本按 ELF `.rela.plt/.rela.dyn` 的 `r_offset`(GOT) 建
  GOT→符号名映射，再解 `adrp+ldr` 桩（**注意 imm12 要 ×8**，64 位 ldr 是缩放立即数，
  忘了乘会得到 0x2a117b 这种非对齐地址）。
- `tools/where.py` 只对我们自己的 `build/inotia4_nx.elf` 有效；libgame 的偏移要
  用 `tools/disas_at.py data/libgame.so <off>` 看 nearest export。

### 改动（src/main.c）
1. `touch_state_tick()`（hud_tick 每帧）：读 `[vb+0x2b2eb0]`
   （`TouchHandle_GetMovingControl` 的全局槽），若控件不可读或 `+0x50` 的 data
   为空/不可读 → 把槽清 NULL，日志 `ui: dropped stale moving control %p (data %p)`。
   不清正常拖动（data 有效时不动）。
2. GOT override 新增 `ControlItem_GetMoving` → `ctrlitem_get_moving_safe()`：
   等价实现 + data 为 NULL 时返回 0（"没在拖动"），日志
   `ui: ControlItem_GetMoving(%p) without a data block -> 0`。
   用现成 `so_set_overrides()`（必须在 `so_resolve()` 之前注册）。

config.ini `b3076640…`、save 18 文件 / 3,080,145 B 未变。实机由用户用 DBI 从 dist 拷卡。

## 18:50 需求：技能点 / 能力点 / 货币使用时数值不减少

### 引擎里的三个唯一写入口（反汇编确认）
- `CHAR_SetSkillPoint(ch, v)` = `*(u8 *)(ch + 0x328) = v`（getter 是 ldrb，8 字节）
- `CHAR_SetStatusPoint(ch, v)` = `*(u16 *)(ch + 0x32a) = v`
- `INVEN_MinusMoney(v)`：钱是 `[0x29f0f8]` 指向的 s64，`subs` 后写回，
  返回 1 = 扣款成功 / 0 = 余额不足；加钱走 `INVEN_AddMoney`（不动）。
- `find_callers_at.py` 对三者都报 **0 references** → 引擎内部全部经 PLT 调用，
  所以 GOT override 能拦住（没有直接 BL 需要 patch call site）。

### 实现（cfg.lock_points，默认 1，不需要改 ini）
- `lock_set_skill_point`：`cfg.lock_points && input_hud_present()` 且新值 < 旧值 → 丢弃，
  日志 `cheat: skill point %u -> %d kept`；否则调 real。
- `lock_set_status_point`：同上（u16），日志 `cheat: ability point ...`。
- `lock_minus_money`：游戏内直接返回 1（假装付款成功、不写钱），
  日志 `cheat: payment of %ld ignored`；游戏外走 real（读档/初始化不受影响）。
- 升点、重置技能、捡钱等**增加**路径全部走原函数。
- 注册在 `so_resolve()` 之前（`so_set_overrides(lock_overrides)`），
  real 指针用 `so_try_find_addr_rx` 先取好，避免自身递归。
- 开关：`config.ini` 的 `lock_points=0` 可关（默认值在 config.c 里给 1）。

### 部署
NRO `4dd4534d72622321beb6a5f0b67eb6f6`，build / dist / Eden sdmc 一致；
config.ini 与 save 未动。实机需用户用 DBI 从 dist 拷卡。

## 23:30 能力点锁修好：它根本不在 CHAR+0x32a

用户第一版反馈「技能点和金币不减少了，能力点还少」。

### 关键事实（诊断日志 + 反汇编）
- 诊断证明：`CHAR_GetStatusPoint(ch)` 全程返回 **3** 不变；
  `CHAR_SetStatusPoint` **一次都没被调用**（加了无条件打印 + 24 条限额，日志里 0 条）。
- 加点的真正路径是 `StatDivide_*` 这组：
  ```
  StatDivide_AddStat(i):                 // 点 + 号
      [0x2d2e58] -= 1                    // 页面自己的剩余点数（int64，bss）
      [0x2d2e60 + i*8] += 1              // 本页临时分配（5 个属性 × 8 字节）
      SV_InfoStatPointSet([0x2d2e58])    // 镜像进脚本变量，UI 标签读它
  StatDivide_SubtractStat(i):            反向
  StatDivide_Init():                     [0x2d2e58] = CHAR_GetStatusPoint()，再镜像
  StatDivide_OKApply():                  CHAR_SetStatMain(...) ×N + CHAR_SetStatusPoint([0x2d2e58])
  ```
  → 角色字段只在「确认」时同步，而 UI 显示的是 `[0x2d2e58]` / SV 镜像。
- `StatDivide_AddStat` 没有任何 `.rela` 重定位（靠 `.rela.dyn` 0x29f850 附近的函数指针表调），
  没法用 GOT override；但 `SV_InfoStatPointSet` 有 PLT 槽（0x2a4f18）→ 从镜像侧下手。

### 修法
- hook `SV_InfoStatPointSet(v)`：若 `v < stat_left_cache`，把 `[0x2d2e58]` 写回缓存值，
  并把缓存值再喂回引擎（同一帧生效，UI 不会看到减一），日志
  `cheat: ability point 2 -> 3 kept`。
- `lock_points_tick()` 每帧维护 `stat_left_cache`（`[0x2d2e58]` 只增不减），并且
  对队伍 3 个角色（`[0x2d0600 + i*8]`）的 `+0x32a / +0x328` 做同样的只增不减兜底。
- 保留两个**限次诊断**（各 20/24 条）：`cheat: SetStatusPoint(...) was N`、
  `cheat: GetStatusPoint(...) -> N`。它们是一次性的，用来下次判断页面读了哪一路。

### 实测（日志 23:27–23:31，build 23:27:08）
```
cheat: ability point 2 -> 3 kept     ×8
cheat: skill point 3 -> 1 kept / 3 -> 0 kept
cheat: payment of 60 ignored
```
三项同时生效，用户确认「可以了」。

### 部署
NRO `fb77913dfb0cd4ffb680fa1ad686d144`，8.88 MB（比上版 8,876,672→略大），
build / dist / Eden sdmc 一致。实机需用户用 DBI 从 dist 拷卡。

### 教训
「某个数值锁不住」先证伪**字段假设**：加无条件打印，看 getter 到底返回什么、setter 到底被没被调。
这次两条日志直接推翻了「能力点 = CHAR+0x32a」的假设，比继续猜 UI 布局快得多。
另一个通用点：引擎的 UI 页面常把「待提交的编辑」放在自己的 bss 计数器里再镜像到 SV，
只 hook 最终落地字段是拦不住的。
