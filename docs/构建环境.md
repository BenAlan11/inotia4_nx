# 构建环境：Windows 上从零到出 `.nsp`

> 目标：在这台 Windows 机器上编出 `inotia4_nx.nsp`（游戏程序）和 `inotia4_nx.nro`（启动器）。
> 结论先说：**你只需要装一个 Docker Desktop，别的都不用装、不用编。**

---

## 0. 那篇博客讲的是什么

你发的那篇是《如何从源码编译构建大气层》，链路是：

```
devkitA64 + devkitARM + switch-dev  →  export DEVKITPRO  →  make  →  atmosphere.zip
```

它编的是**固件本身**（fusee / exosphere / mesosphere / stratosphere）。本端口是两个自制程序：

| 产物 | 位数 | 工具链 | 依赖 |
|---|---|---|---|
| `inotia4_nx.nsp` | 32 位 AArch32 | devkit**ARM** | libnx32 + AArch32 Mesa |
| `inotia4_nx.nro` | 64 位 AArch64 | devkit**A64** | libnx（镜像自带） |

两者都靠 **devkitPro 的工具链**，但博客里那些包（`switch-glm`、`switch-libjpeg-turbo`、`hactool`、`pip install lz4`）本项目**一个都不用**。真正需要的 devkitARM / devkitA64 / switch-tools，官方 Docker 镜像里已经装好。

---

## 1. 只需要一样东西

| 需要 | 状态 | 说明 |
|---|---|---|
| Docker Desktop | **要你自己装**（管理员 + 重启） | ~1.5 GB，唯一的手动步骤 |
| `libnx32`（32 位 libnx） | **已就位** | `third_party\libnx32\`，13.4 MB 预编译包 |
| AArch32 Mesa 26.2 | **已就位** | `portlibs32\`，11.5 MB 预编译包 |

两个依赖都已经解压进工程了，`runtime.mk` 的 Mesa 26 分支要的 10 个库全部齐全（`-lEGL -lGLESv2 -lGLESv1_CM -lglapi -lmesa_util_c11 -lblake3 -lmesa_util -lmesa_util_simd -lexpat -lz`），`libnouveau_horizon.a` 也在——它决定 runtime.mk 选 26 而不是 20。

**不需要**编 libnx32，**不需要**编 Mesa。自己编这两个东西要 Docker + 容器，Mesa 那部分在 x86 上模拟 ARM，**一小时起步**；官方 release 有预编译包，已发布的那些端口（蜘蛛侠、PvZ、Asphalt 8…）用的就是这个。

> 需要重新取（比如上游更新了）才跑 `.\tools\get-deps.ps1`。它走 `api.github.com` 而不是 `github.com/.../releases/download`——后者在国内常被墙（`CONNECT 502`），前者通。

## 2. 三步

### 2.1 装 Docker Desktop

```powershell
winget install -e --id Docker.DockerDesktop
```

装完**重启**，启动 Docker Desktop，等右下角显示 *Engine running*。
（设置里保持 *Use the WSL 2 based engine* 勾选即可，你不需要手动开 WSL 终端。）

### 2.2 取依赖（已经做完了，可跳过）

`third_party\libnx32\` 和 `portlibs32\` 已经解压好并核对过。只有在想更新到上游新版本时才需要：

```powershell
.\tools\get-deps.ps1
```

它会：下载两个 zip、解到 `third_party\libnx32\` 和 `portlibs32\`、摊平包里的顶层目录、打印每个关键文件的 ok/MISSING。

### 2.3 构建

```powershell
.\tools\build-docker.ps1          # 32 位游戏程序 -> inotia4_nx.nsp
```

它执行的就是 `runtime/tools/docker_build.sh` 里那条 `docker run`，只是把路径换成了 Windows 形式（**不要**在 Git Bash 里跑，MSYS 会把 `-v C:/...` 翻译坏）。

启动器（64 位，需要 `devkitpro/devkita64` 镜像，第一次会自动拉）：

```powershell
cd launcher
.\build.sh
```

> 启动器目前只有 shell 版脚本；在 PowerShell 里等价于：
> ```powershell
> docker run --rm --platform linux/amd64 `
>   -v "${PWD}\..:/work" -v "${PWD}\..\runtime:/runtime:ro" -w /work/launcher `
>   devkitpro/devkita64:latest bash -lc "make -j`$(nproc) A32=/runtime"
> ```

## 3. 目录最终长这样

```
inotia4_nx\
├── portlibs32\            <- Mesa 26.2 预编译（libEGL.a, libGLESv1_CM.a, libnouveau_horizon.a…）
├── third_party\
│   ├── libnx32\           <- libnx32 预编译（lib\libnx.a, include\switch.h）
│   └── _dl\               <- 两个 zip 的缓存
├── runtime\               <- android32（MIT）
├── source\                <- 端口代码
├── tools\
│   ├── get-deps.ps1       <- 下预编译依赖
│   ├── build-docker.ps1   <- 编 32 位程序
│   └── verify.sh          <- 不用工具链的自检
└── Makefile
```

## 4. 虚拟化：`HCS_E_HYPERV_NOT_INSTALLED`

Docker Desktop 的 Linux 引擎是一个 WSL2 虚拟机，WSL2 又要 Windows 的 Hyper-V 虚拟化层。报这个错说明**虚拟化层没启动**，不是 Docker 本身的问题。

先分辨两种情况（`systeminfo` 最后几行）：

| 输出 | 含义 | 怎么办 |
|---|---|---|
| `固件中已启用虚拟化: 否` | BIOS 里 VT-x/AMD-V 关了 | 重启进 BIOS 打开（Intel VT-x / AMD-V、SVM Mode） |
| `固件中已启用虚拟化: 是`，且**没有**出现「已检测到虚拟机监控程序」 | BIOS 没问题，是 Windows 功能没开 | 见下面的命令 |
| 出现「已检测到虚拟机监控程序。将不显示 Hyper-V 所需的功能。」 | 虚拟化层已在运行 | 问题在别处，看 Docker 日志 |

第二种情况的修复（**管理员** PowerShell）：

```powershell
dism.exe /online /enable-feature /featurename:VirtualMachinePlatform /all /norestart
dism.exe /online /enable-feature /featurename:Microsoft-Windows-Subsystem-Linux /all /norestart
bcdedit /set hypervisorlaunchtype auto
```

或者更省事，一条：

```powershell
wsl --install --no-distribution
```

**然后必须重启**。重启后确认：

```powershell
docker info --format '{{.ServerVersion}}'
```

打印出版本号（而不是 500 或 unable to start）就说明引擎起来了。

## 5. 报错对照表

| 报错 | 原因 | 处理 |
|---|---|---|
| `docker: command not found` | 没装或没重启 | 装完重启，重开 PowerShell |
| `Docker Desktop is unable to start` | WSL 组件太旧，或**虚拟化没启用** | 先 `wsl --update`；若还报 `HCS_E_HYPERV_NOT_INSTALLED` / `hasNoVirtualization`，见下面的「虚拟化」一节 |
| `the docker engine is not running` | Docker Desktop 没启动 | 启动它，等 *Engine running* |
| `libnx32 not found` | 没跑 `get-deps.ps1` | 先跑它，或用 `-Libnx32 D:\nx\libnx32` 指定 |
| `portlibs32\lib\libEGL.a is missing` | 同上（会退化成 null 渲染器） | 跑 `get-deps.ps1` |
| `undefined reference to glMatrixMode` 等一堆 `gl*` | 用的是 mesa32(20.1)，它只链 `-lGLESv2` | 换成 mesa-switch32（26.2），`get-deps.ps1` 默认就是它 |
| 运行时 `Undefined System Call 0x5E` | NPDM 没放开 cache 系统调用 | 本工程 `runtime/npdm.json.in` 已含 `0x5D/0x5E/0x5F`，若仍报说明 runtime 版本旧 |
| 构建里 `fatal error: switch.h: No such file` | libnx32 没挂上 | 检查 `third_party\libnx32\include\switch.h` 是否存在 |
| `-v` 参数被改成 `/c/Users/...` | 在 Git Bash 里跑了 | 用 PowerShell |

## 6. 为什么不是「原生装 devkitPro」

原生装（博客那条路）对本项目有三个坑：

1. **devkitPro 官方仓库被 Cloudflare 挡**：`pkg.devkitpro.org` 对脚本/curl 返回 403，只能靠浏览器或 pacman 客户端；便携解包这条路走不通。
2. **原生 devkitARM 缺 ARMv8-A multilib**：32 位 Switch 代码要 `-march=armv8-a+crc+crypto`，官方镜像里的 devkitARM 是带 Switch multilib 的特别构建，Windows 版没有保证。
3. **libnx32 与 Mesa 的构建脚本写死了 `docker run`**：就算原生装了工具链，它们的脚本照样调 Docker。

所以原生路线在这个项目上省不了事，反而多两个不确定性。

## 7. 关于这台机器上的沙箱

我这边的执行环境有以下限制，所以**安装动作必须由你来点**（都只需要一次）：

- 没有管理员权限 → 装不了 Docker Desktop；
- `wsl.exe` 被安全策略拦截（Security Center → Command Security → Program Blacklist）；
- `pkg.devkitpro.org` / `downloads.devkitpro.org` 对 curl 返回 Cloudflare 403。

Docker 装好之后，`get-deps.ps1` 和 `build-docker.ps1` 我可以直接跑——它们只调用 `docker.exe`，不碰 `wsl.exe`。
