# Inotia 4 → Nintendo Switch 移植路线复核

> 复核对象：`andy4gjf_313472.apk`（Inotia 4，v1.3.7 / versionCode 14）
> 参考实现：`boraeskicioglu/spiderman_total_mayhem_nx` + 其 runtime `aks796/android32`
> 日期：2026-10-27

---

## 1. 先修正上一轮的结论

上一轮我说"Switch 没有 GLES1 驱动，必须自己编 gl4es"——**这句话是错的**。

Spider-Man Total Mayhem 的 README 明确写：

```
- OpenGL ES 1.1 through Mesa/Nouveau.
```

而 `android32` 的 README 写：

```
- Graphics: EGL and GLES on Mesa's nouveau driver (mesa32 or mesa-switch32),
  or a null renderer.
```

它的 `imports.c` 里**根本没有 gl\* 符号**（文件头注释："gl* aside: the GL layer serves those"），全部交给 `source/gl_mesa.c` 处理。也就是说：

**Mesa 的 GLES1 state tracker 在 Switch 上是可以用的**，`libGLESv1_CM.so` 这一层由 mesa32 / mesa-switch32 提供，不需要 gl4es。Spider-Man 是纯 GLES1 游戏，已经真机 60FPS 跑通了。

这一条推翻后，Inotia 4 的难度评级要下调一档。

---

## 2. 关键发现：有一条现成的 32 位路线

`android32` 是**多个移植共用的 runtime**（14 个项目在用：Disney Crossy Road、PvZ Touch、Angry Birds Space、Asphalt 8、Sonic All-Stars、Dead Space、The Amazing Spider-Man 2、Space Hulk 等）。

它已经实现了：

| 层 | 文件 | 说明 |
|---|---|---|
| .so 加载 | `so_util.c`、`crt0_reloc.c`、`codespace.c` | 映射 + 重定位 + 构造函数，32 位 PIE |
| bionic | `bionic_*.c`（18 个） | pthread、stdio、socket、signal、zlib、wchar、C++ ABI 全套 |
| **伪 Java VM** | `jni_core.c` + `jni.h` | 类/对象/字符串/数组/字段，**不需要真 JVM** |
| NDK shim | `android_ndk.c` | looper、window、asset、configuration |
| **GL/EGL** | `gl_mesa.c` / `gl_null.c` / `gl_blit.c` | 直连 Mesa，含首帧错误日志与自检 |
| OpenSL ES | `opensles.c` + `rt_audout.c` | OpenSL 接到 audout |
| 手柄 | `rt_pad.c` | 控制器读取 |
| 生命周期 | `rt_applet.c`、`watchdog.c` | HOME/休眠、卡死检测 |
| 崩溃日志 | `exc_handler.c` | 写 `crash.log` |
| APK 解包 | `dcr_setup.c`、`rt_apkfind.c` | 从 SD 上的 APK 自动找库、带进度条解包 |
| 启动器 | `launcher/` | 64 位 NRO + sphaira forwarder |

**对一个端口，作者只需要写**：

1. `source/port_config.h` —— 包名、路径、ABI 目录等（已按此格式起草，见 `port_config.h`）
2. `source/imports.c` —— **由 `tools/gen_imports.py` 自动生成**，不手写
3. JNI 表 —— `jni_method_defs[]`、`jni_field_defs[]`、`jni_class_supers[][]`、`jni_missing_classes[]`
4. `port_load(const char *apk)` 和 `port_run(void)`
5. `dcr_boot_frames()`

这比 lnsor_nx 那套（要自己写 libc shim、自己写 jni_fake、自己接 EGL）省掉的工作量是数量级的。

### 为什么这条路对 Inotia 4 成立

`android32` 只吃 `armeabi` / `armeabi-v7a`。而这个 APK 恰好**同时带 32 位和 64 位**：

```
lib/armeabi-v7a/libgame.so     1,789,328  ← 走这条路
lib/armeabi-v7a/libHercules.so   527,008
lib/arm64-v8a/libgame.so       2,798,792  ← 留给自建 64 位 so-loader 方案
```

所以不必自建 64 位方案，直接用 v7a 那套进成熟的 runtime。

## 3. 这个 APK 的真实工作量

### 3.1 58 个 JNI 入口，按必要性分三档

从 `libgame.so` 导出的 `Java_*` 符号实际提取（完整清单见 `jni_surface.txt`）：

**A 档 · 内核（约 16 个，必须真实现）**
`CWrapperKernel` 的 `nativeStart / nativeProcess / nativePause / nativeResume / nativeDestroy / nativeSurfaceRecreated / nativeOnScreenSizeChanged / nativeStartClet / nativePauseClet / nativeResumeClet / nativeDestroyClet`，
`CWrapper` 的 `nativeInitialize / nativeSetClass / nativeFinalize`，
`CWrapperData` 的 `nativeInitialize / nativeSetScreenSize / nativeFinalize`，
`CCommonAPI` 的 `nativeInitialize / nativeUninitialize`，
`CEventHandler` 的 `nativeEventHandlerInitialize / nativeRemoveAll`。

这批决定"能不能出画面"。`nativeStart` 是主循环入口，`nativeSurfaceRecreated` 说明 GL 上下文由外部创建后通知它。

**B 档 · 平台服务（约 10 个，部分要实现）**
- `CFont.nativeFontInitialize`、`nativeCreateFromTypeface` —— **字体，最大不确定项**（见 3.3）
- `CSensor.nativeSensorInitialize` —— 直接返回 0
- `CTextInput.nativeCallback` / `CUserInput.nativeCallback` —— 输入，要接 `rt_pad`
- `CWrapperHttp.*`（3 个）—— 单机不需要，返回"连接失败"即可
- `CUtility.nativeWebviewCB` —— 桩
- `WrapperUserDefined.nativeExitCB` —— 退出

**C 档 · Com2uS 平台 SDK（约 32 个，整体桩掉）**
`ActiveUser.*`（6）、`InAppV4.*`（10）、`Mercury.*`（5）、`HubBridge.*`（2）、`MainActivity.nativeHerculesInit / nativeUseFmod`。

这一档是登录、计费、推广、推送。`libHercules.so` 干脆不加载，让这些入口返回"失败/未初始化"。单机流程不依赖它们——但**首次启动是否会卡在 Hive 登录页**需要实测，可能要 hook 掉对应分支。

### 3.2 音频：要自己写，但有现成参考

`.so` 里**没有** OpenSL ES、没有 FMOD，声音走 `CS_mdaSoundCreate/Play/Stop/SetVolume` 这类封装，一路回调到 Java 的 `SoundPool`（dex 里出现 8 次）和 `MediaPlayer`（7 次）。资源是 Ogg Vorbis（`.jpg` 伪装，无加密）。

做法：在 JNI 表里实现 `android/media/SoundPool` 和 `MediaPlayer` 的常用子集，底层接 `stb_vorbis` + `rt_audout`。Spider-Man 端口的 `source/tm_audio.c` + `stb_vorbis.c` 就是同一件事的成品，可以直接照结构抄。

### 3.3 字体：唯一的真正未知

`CFont.nativeFontInitialize` / `nativeCreateFromTypeface` 说明字形来自 Android 的 `Typeface`。而 `.so` 的未定义符号里**没有任何 FreeType/Skia 符号**，说明它自己不栅格化字形，只能靠 Java 侧给位图。

两条路，取决于反汇编 `CS_font*` 的调用约定：

1. **优先**：hook 掉引擎的字体入口，换成 stb_truetype 自己栅格化，绕开 Java 的 `Paint/Canvas`。工作量小，但要逆向出字形位图的格式（宽高/步长/像素格式/基线）。
2. **兜底**：在 JNI 表里实现 `android/graphics/{Typeface,Paint,Canvas,Bitmap}` 的最小可用子集。工作量大得多。

这一项建议在 stage1b 出画面后立刻验证（先看菜单有没有字），因为它决定整个项目是"两周能玩"还是"要啃一个月"。

### 3.4 触摸：rt_pad 已有骨架

引擎靠 `CS_knlGetTouchCount` 拿触点，Java 侧 `CUserInput` 送事件。做法是把 Switch 摇杆/按键在 `rt_pad` 之上合成 1~2 个虚拟触点，喂给 `CUserInput.nativeCallback`。Spider-Man 已经做了"controller-to-touch"桥接和菜单光标，是直接可参照的实现。

### 3.5 路径与资源

引擎按 `/sdcard/Android/data/<包名>/files/resources/<...>` 取资源（`GetPackageName` 由 Java 提供，包名要照实返回）。`mkdir` 在导入表里，目录它自己会建，但**首次运行要把 APK 里 `assets/common/game_res` 解到那个目录**——这是 `dcr_setup` 的 setup plan 要写的一段（原版是 Java 干的活）。

`RT_PATH_SD_SUBDIRS` / `RT_PATH_EXTRA_DIRS` 要覆盖 `Android/data/<包名>/files` 这条链。

## 4. 分阶段验证（沿用 Spider-Man 的 stage 命名）

每一阶段都以"真机能跑"为通过标准，失败了就停，不往后堆。

| 阶段 | 目标 | 通过标准 |
|---|---|---|
| stage0 | APK 识别、解包 `libgame.so`、加载、跑构造函数 | `debug.log` 里能看到 JNI 请求清单（开 `log_jni`） |
| stage1a | 补 A 档内核桩，调用 `nativeStart` | 不再崩在空指针，进入自己的主循环 |
| stage1b | EGL + GLES1 首帧（`gl_mesa.c` + `gl_selftest`） | 出画面（哪怕是黑底或错色） |
| stage1c | 资源路径映射 + 解包 assets | 出现标题画面 |
| stage1d | 触摸合成 | 能进菜单、能开新游戏 |
| stage1e | 音频（SoundPool/MediaPlayer → stb_vorbis + audout） | 有 BGM 和音效 |
| stage1f | 字体 | 文字不是方块/空白 |
| stage1g | 存档与设置持久化 | 退出再进进度还在 |
| stage1h | 性能（`dcr_boost`、帧率、分辨率） | 稳定 60FPS @720p |

stage1b 和 stage1f 是两个真正的关卡，其余都是工程量。

## 5. 风险清单

| 风险 | 影响 | 应对 |
|---|---|---|
| 首次启动被 Hive 登录页拦住 | 卡在联网页，进不去游戏 | hook 掉登录分支；或伪造 ActiveUser 返回"已登录" |
| 字体走 Java `Paint/Canvas` 且格式难逆 | 文字全丢，需实现 2D 光栅化 | 尽早验证；优先 hook 引擎字体入口 |
| 引擎内部有 Java 侧解包/校验逻辑 | 资源目录不完整，读档失败 | 对照 dex 反编译 Java 流程复现 |
| GLES1 固定管线在 nouveau 上的兼容问题 | 混合/光照/点精灵异常 | 已有 14 个端口踩过，`gl_mesa.c` 有错误日志 |
| 只支持 v1.3.7 / versionCode 14 | 换版本可能偏移全变 | 在启动时校验 versionCode，不匹配就报错退出 |

## 6. 结论

- **能实现，且比上一轮评估的容易**：GLES1 有 Mesa 兜底，bionic/JNI/EGL/OpenSL/手柄/启动器全都是现成的 runtime。
- **主工作量不在"跑起来"，在"补 JNI 表"**：58 个入口里 32 个可以整体桩掉，真正要写的是 16 个内核 + 音频/字体/触摸三块。
- **建议路径**：用 `armeabi-v7a` 的 `libgame.so`，把 `aks796/android32` 作为 `runtime/` 子模块，照 Spider-Man 的 `port_config.h` + `imports.c`（自动生成）+ `port_load/port_run` 结构起项目。
- **最先做的一件事**：stage0 + stage1a，只为拿到"游戏到底请求了哪些 Java 类和方法"这份清单。这份清单出来之前，任何工作量估计都是猜的。

> 法律提醒：`.so`、`assets`、存档都不能随成品分发；`android32` 是 MIT，但游戏本身仍需用户自备正版 APK。
