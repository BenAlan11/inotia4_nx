CHANGES SINCE 20261108-1941
  One fix, in src/main.c. Full log: .workbuddy/memory/2026-11-08.md.

  Story / class-description body emphasis colour. Hints, quests and skill
  descriptions keep their $X codes (X_TEXTCTRL) and were already coloured;
  the story body goes through TEXTCTRL2 and was not.

  Evidence: the new `subraw:` diagnostic showed
  `subraw: y485 len93 col ffffffff codes 0 '原本是高贵的骑士...'` -- the
  string handed to nx_sub_string has NO $ codes and a white pen. Reading the
  engine:
    * GRPX_DrawSubStringWithFont2 (0x1223a4) has only three call sites, all in
      TEXTCTRL2_DrawAsStep (0x1daf98) / TEXTCTRL2_Draw (0x1db03c).
    * TEXTCTRL2_LineProcess (0x1da778) CONSUMES each "$X" into a 32-byte
      display unit's colour field (+8). It never writes back to the string
      buffer; the original text is still at ctrl+0x00.
    * TEXTCTRL2_Draw does, for every span: ldr w0,[unit,#8];
      GRPX_GetColorFromGRP (0x1227a0, output 0xFFBBGGRR);
      GRPX_SetFontColor (0x122848); then
      GRPX_DrawSubStringWithFont2(original + unit.offset, unit.len, ...).
    * Our hook therefore receives a CODE-FREE VIEW of one span. The emphasis
      colour survives ONLY in GRPX_SetFontColor's argument, while the port was
      reading GL_CURRENT_COLOR -- always white in this shell. No $ code was
      lost by any recent build; the hint path simply uses a different system.

  Fix: hook GRPX_SetFontColor (added to the so_override table). The hook
  records w0 only when its return address is inside TEXTCTRL2_Draw /
  DrawAsStep (0x1daf98..0x1db288) and forwards EVERY caller to the real
  function (resolved with so_try_find_addr_rx; so_set_overrides only registers
  a set and does not edit the ELF symbol table, so no recursion).
  nx_sub_string now uses __builtin_bswap32() of that value as its pen -- the
  same (a<<24)|(b<<16)|(g<<8)|r -> 0xRRGGBBAA conversion tctrl_colour()
  already uses -- and falls back to GL_CURRENT_COLOR when no span colour was
  set this frame. text_colour() still lifts the opaque-black base $B to white,
  so ordinary lines stay white and only emphasised spans turn coloured. One
  callback per span gives several coloured runs per line, like the original.
  Logs: `story: font colour %08x`, `story: span pen %08x -> %08x`.

  Also: `subraw:` now de-duplicates by text and has a 60-line budget, so a
  static class-description page cannot consume it before a real dialogue.

THINGS THAT BROKE AND MUST NOT BE REPEATED
  * Calling the engine's per-scene key handler from port code -- directly,
    through the 0x29eb90 slot, or after PT_LOAD|PF_X validation -- stalls the
    frame loop (0 FPS / nan ms, debug.log stops with no watchdog line).
    menu_key_press() was DELETED. Do not reintroduce a guarded version.
  * POPUPSTATE_Exist() returns 0 on the character page. Any "is this a popup
    page" test based on it misclassifies that page as AB_MENU.
  * Assuming UIPopupMsg is the only message box, or matching the
    shortcut-assign page's slots / UIChoice's rows by control id. Their ids
    change between sessions. Match the event proc or the tree shape instead.
  * Reading UIPopupMsg's OK control (0x2b8d98) after the box closed: stale.
  * Assuming a one-shot rect write sticks on the shortcut-assign page -- it
    resets its rects every frame, so quick_layout_frame() re-applies.
  * Incremental builds after changing config.h OR text.h. Use --clean.
  * so_try_find_addr_rx() returns uintptr_t; assigning it to void* without a
    cast is a hard clang error (-Wint-conversion).
  * Parking the d-pad / action-disc control rects off-screen to "stop them
    answering touches". The user rejected this: the rule already exists in
    hud_touch_blocked(), and input.c drives those objects directly.
  * Filtering quads by screen rectangle to hide UI. Suppress the draw call
    site, never mask an area. A pure ra range is fine for the wheel but NOT
    for HUD buttons sharing a call site -- use the control's own rect there.
  * Maintaining a hand-written $X colour-code table. The engine's table at
    +0xbb9c8 is the only source of truth for the X_TEXTCTRL path.
  * Assuming the X_TEXTCTRL $X table also drives story text. TEXTCTRL2 uses
    display units + GRPX_SetFontColor, a completely different mechanism.
  * Using GL_CURRENT_COLOR as the story body's pen. It is always white here;
    the engine's own font colour state is the source.
  * Ordering the four face keys by NS button name from qt-config.ini: the
    14:23 attempt reversed the physical A/B. Use the user's tested order.

    ship hide_pad_zone = 0.

    config.prod.ini, dist/switch/inotia4/config.ini, Eden sdmc config.ini.
  * The Eden sdmc config.ini also carries the user's log_level = 3 and
    tap_script = "960,919@600". Do not overwrite it with the production file.

  * Do not edit %APPDATA%\eden\config\qt-config.ini.

KNOWN GAPS
  * This build's story-emphasis fix and the RT A/B order have NOT been
    play-tested. If `story: font colour ff000000` is the only value seen, the
    TEXTCTRL2 unit colour is not reaching GRPX_SetFontColor as expected --
    check TEXTCTRL2_LineProcess before changing anything else.
  * A on a UI page other than a UIPopupMsg / UI_PopupProcess box is ignored.
  * The R swap assumes the HUD reads shortcut slots as array[page+i].
  * Hiding the field HUD's swap icon uses the draw call's anchor near
    1059,313; a future layout change could move that anchor.
  * dlg_probe still has a 16-row table; only subraw/rich logs are reliable
    for story dialogue.
